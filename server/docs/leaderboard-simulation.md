# 排行榜模拟数据

适用范围：学力、学习时长、掌握词汇的周榜和总榜。旧版无参数榜单接口、听写完成后的学力排名也使用同一套排序。

## 人数与换周

- 以北京时间周一 00:00 为一周起点，每周重置模拟名单。
- 每个指标独立确定 700–2100 人的周目标，再分配成七天增量，每天至少增加 70 人，累计不超过周目标。
- 同一指标的周榜、总榜共享名单；真实用户的历史成绩不重置。
- 名单、昵称、每日增量和活动计划由指标、周编号及成员编号确定。同一天重复刷新、多实例、重启或中间几天无人访问，都不会重复增加人数。
- 模拟数据在服务端查询时生成，不创建真实账号，不写入学习记录、同学关系、动态或注册/活跃人数统计。

## 分数与保护规则

- 使用真实用户成绩独立计算保护线，不用混合榜单反推阈值。
- 真实用户达到 20 人时，模拟分数上限为真实第 20 名的分数；同分时所有真实用户优先，真实前 20 名的身份、顺序和名次不受模拟数据影响。
- 在分差允许时，模拟分数下限为真实末 5 名中最高分加 1。
- 只有 20–24 人、末尾同分或无足够整数分差时，优先保护前 20 名，不强行超过末 5 名。
- 不足 20 人时，模拟分数不高于现有真实用户的最低分，同分真实用户优先。没有真实成绩时使用低分起始区间。
- 每个模拟成员的每日活动进度可以增加或保持不变，映射到当前真实分数允许的区间。若真实保护线因订正等原因下降，模拟展示分数会同步受限，保护真实前 20 名优先。

真实用户的“我的排名”和距上一名差值按照混合榜单计算，其真实分数保持原值。接口额外提供 `participantCount`、`simulatedParticipantCount`，每条排名使用 `isSimulated` 区分模拟记录。

## API 性能

- 模拟数据不发送给 PostgreSQL，不参加数据库排序，不增加数据库写入或查询次数。与原版一样，一次读取配置、一次查询真实排名。
- 真实排名查询只额外返回保护线和末五名等必要数据，最多取配置人数与 20 的较大值、末五名及本人，不全量传回用户数据。
- 进程内最多缓存三个每日名单和六个指标/周期分数区间，不按访问用户数增加缓存。日期或真实分数区间变化时替换旧缓存。
- 热请求不重复生成昵称、不序列化整批模拟名单、不重新排序模拟分数；本人排名与差值通过二分查找，展示榜单只合并所需的前 N 名。
- 不缓存真实榜单响应，因此真实学习分数、保护线、配置人数仍即时生效。
- 冷缓存仍有一次性 CPU 开销：本机 2100 人名单首次生成和计分约 5.85ms，热缓存查找及二分平均约 0.00054ms；这些数字不包含原有数据库查询。
- 20/1000/10000 真实用户、六种榜单共 7200 次交错对比中，P50 最大增量 0.209ms，P95 最大增量 2.211ms。详见 [性能报告](leaderboard-performance.md)，不是生产环境的零耗时承诺。

## 发布与验证

本次只需重新构建、部署 API 服务，不需要数据库迁移、定时任务或小程序更新。

- `npm --prefix server test`：覆盖三个指标连续三年的周人数约束、每日增长/不变、刷新一致性、北京时间换周和跨年。
- `npm --prefix server run typecheck` 与 `npm --prefix server run build`。
- `server/src/lib/leaderboard-simulation.integration.ts`：必须在本机端口 55436、数据库 `gotit_leaderboard` 的空白隔离数据库中运行。覆盖六套榜单、前二十保护、末五名分数区间、20/21 人及同分边界、保护线下降、旧版接口与听写排名一致、并发及真实账号隔离。
- 原有 `leaderboard.integration.ts`、`leaderboard-limit.integration.ts`、`social.integration.ts` 同样在隔离数据库回归。
- 性能对比使用 `leaderboard-simulation.performance.ts`，通过 `LEADERBOARD_BASELINE_REF` 指定模拟功能之前的 Git 提交，避免拿已优化版本充当旧版基线。
